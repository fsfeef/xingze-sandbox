## 1. 目标（一句话）

1.1 同一座星泽市里，两个或更多玩家能互相看见对方走路 / 开车；对方是真人角色模型，不是胶囊人。
1.2 渲染还在各人手机上跑，服务器只同步位置和动作，不跑渲染、不下发城市场景。
1.3 第一 milestone 只做“同城互相可见”（见 §5），跑通再谈后面的事。

## 2. 现状锚点（设计以此为准，写代码时先复核一遍）

2.1 模式：`app.js` 的 `state.mode` 有四种：`aerial`（航拍）、`walk`（走路）、`fly`（飞行）、`drive`（开车）。多人只同步 `walk` / `drive` 两种；`aerial` / `fly` 的玩家对别人不可见（见 §4.7）。
2.2 走路：`state.pos` 是相机位置（眼睛），`state.lookYaw` 是朝向；速度走路 7 m/s、跑（Shift）20 m/s；走路时 `state.pos.y = groundY(x, z) + 1.7`，`groundY` 在六区模式下调 `sixLoader.groundHeightAt(x, z)`，非六区为 0。
2.3 开车：`car = { x, z, heading, speed }`，`car.x += sin(heading) * speed * dt`，`car.z += cos(heading) * speed * dt`；上限 33.3 m/s（即林萧定的 120 km/h），倒车下限 -6 m/s；`carGroup.position.set(car.x, gy, car.z)`，`carGroup.rotation.y = car.heading`；车内视角相机在车内局部 (0, 1.35, +0.4)。
2.4 活动范围（六区模式）：`BOUNDS()` 为 `x: [-16500, 16500]`，`z: [-19500, 16000]`，整城约 33 km × 35.5 km。服务器校验就按这个范围。
2.5 行人建模：`people.js` 是程序化拼装体，绝不是胶囊人——头（球）+ 头发 + 眼睛 + 躯干 + 双臂 + 双腿 + 鞋，10 个 `InstancedMesh`（躯干/头/短发/长发/左腿/右腿/左臂/右臂/眼睛/霓虹胸条），48 个 NPC，每人种子不同，衣服 / 发型 / 肤色 / 身高 / 步速全按种子变；步态是逐帧由速度 / 朝向算的（摆臂、迈腿、身体起伏、头预判转向）。
2.6 玩家车：`playercar.js` 的真车是 SUV，深蓝 `#16283F`，无标无牌（牌照位是空的），车身 / 玻璃座舱 / 轮子 / 车灯 / 保险杠 / 格栅 / 后视镜 / 行李架齐全，车内有仪表盘、方向盘、座椅、中控、后视镜；`buildPlayerCar` 目前是模块内部函数，没有导出。
2.7 接线现状：`window.__sandbox` 暴露了 `scene / camera / renderer / state / THREE / sixLoader`，但**没有暴露 `car` 和 `carGroup`**（`car` 是 `app.js` 模块内局部变量，`carGroup` 也是）；`people.js` 只导出 `init / setDisplay / getCount`，NPC 的 48 个实例是固定池，没有“再加一个远程玩家”的接口；`people.js` / `playercar.js` 目前在 `app.js` 里没有静态 import（接线方式见 `playercar.js` 头部注释：动态 import 后 `init(window.__sandbox)`）。
2.8 托管现状：线上是 GitHub Pages 静态站（`linx.is-a.dev/xingze-sandbox/app/`），只能托管静态文件，**放不了 WebSocket 服务器**；多人服务器必须另起一个源（见 §6）。
2.9 当前是纯单机：全仓库搜不到任何 WebSocket / 联网 / 多人代码。

## 3. 架构

### 3.1 总图

3.1.1 客户端（手机浏览器，现有沙盘 + 新增多人客户端模块）←→ WebSocket（`wss://`）←→ 小服务器（单进程 Node.js，内存里只保存在线玩家表，不存库、不存盘）。
3.1.2 服务器不发城市场景、不发楼 / 路 / 地形数据——那些本来就在各人手机上的六区白模包里；服务器只转发“谁在哪、什么姿态”。
3.1.3 一个房间就是整座城，不分区、不分服；以后人多了再按距离分片（见 §3.9）。

### 3.2 服务端选型：Node.js + `ws`（推荐，唯一选型）

3.2.1 选它：Node.js + `ws` 库。MIT 开源免费；`ws` 是 Node 生态最常用的 WebSocket 库，无原生依赖，`npm install ws` 即用；单文件就能跑通（一个 `server.js` 约 150–250 行）；和现有技术栈同源（沙盘本身就是 JS，部署脚本、测试脚本都能复用同一语言）；本机已有 Node v24.22.1，开发零安装成本。
3.2.2 不选的：Socket.IO——功能多（房间、重连、降级）但协议重、包大，首版用不上，留作备选；uWebSockets.js——性能最高但原生编译、部署麻烦，首版没必要；Python（websockets / FastAPI）——要另起语言和依赖，团队现有代码全是 JS；Cloudflare Durable Objects——免费额度好但不是标准 Node `ws` 写法、房间模型不同，改造成本高，列为 §6 的备选，不做首选。
3.2.3 服务端只依赖两样：Node.js 20+（LTS）和 `ws`；不用数据库、不用 Redis、不用任何云服务；重启后在线表清空，玩家重连即恢复——这是可接受的（状态本就是临时的）。
3.2.4 服务端文件位置：`~/workspace/virtual-city/server/`（新目录，与 `app/` 平行，不进 Pages 静态包；`server.js` + `package.json` + `Dockerfile` + `README.md` 四个文件）。

### 3.3 服务器权威程度：只转发 + 轻校验（不做物理权威）

3.3.1 服务器**不跑物理、不算碰撞、不裁决位置真假**：每个客户端自己的走路 / 开车物理仍是权威（`app.js` 现有逻辑不动）。
3.3.2 服务器只做四件事：① 发 id、记在线表；② 转发位置包；③ 轻校验（见 3.3.3）；④ 踢掉超时 / 违规连接。
3.3.3 轻校验清单（缺一不可，校验失败只丢弃该包，不踢人；连续 10 次失败才踢）：
  - 坐标在 `BOUNDS()` 内（`x ∈ [-16500, 16500]`，`z ∈ [-19500, 16000]`），超界包丢弃；
  - 速度合理性：两次包之间位移 / 时间差 ≤ 40 m/s（开车上限 33.3 m/s，留余量；走路 20 m/s 更在内），超了按“瞬移”处理——不转发该包，等下一包（防抖，不直接踢）；
  - 字段类型与范围：`mode` 只能是 `walk / drive`，`yaw` 是有限数，包体 ≤ 1 KB；
  - 频率限制：同一连接每秒最多 30 个包，超了静默丢弃多余包。
3.3.4 为什么不做强权威：强权威要服务器重跑地形高度、碰撞和开车物理，等于把 `six-loader.js` 和 `app.js` 的物理搬上服务器，首版成本过高；轻校验已能挡住手误和一般作弊，位置作弊在“互相可见”阶段不是验收项。

### 3.4 消息协议（JSON，文本帧；版本号 `v: 1`）

3.4.1 传输：WebSocket 文本帧，JSON 编码；首版不用二进制（包小、可读、好调试；以后包大了再评估 MessagePack）。
3.4.2 客户端 → 服务器，共 3 种：
  - `join`：`{ t: "join", v: 1, name: "阿哲", seed: 12345 }`——进城时发一次。`name` 是显示名（见 3.6），`seed` 是外观种子（客户端按玩家 id 哈希生成，见 §4.4）。
  - `update`：`{ t: "update", seq: 1024, ts: 1730000000123, mode: "walk", x: 120.5, z: -560.2, yaw: 2.31, speed: 7.0, moving: true }`——周期发（见 3.5）。开车时 `mode: "drive"`，`speed` 是 `car.speed`（可为负，倒车），`yaw` 是 `car.heading`。`y` 不发——接收方用自己的 `groundY(x, z)` 现算（见 §4.3），省流量还不会错位。
  - `leave`：`{ t: "leave" }`——正常退出（关页面 / 切单机）时发；发不出来也没关系，服务器靠心跳兜底（见 3.7）。
3.4.3 服务器 → 客户端，共 6 种：
  - `welcome`：`{ t: "welcome", id: "p_8f3a", serverTime: 1730000000000, peers: [...] }`——回给刚进城的玩家，`peers` 是当前在线快照（每人最后一条 `update` + 外观）。
  - `peer_join`：`{ t: "peer_join", id, name, seed, mode, x, z, yaw, speed }`——有人进城，广播给其他人。
  - `peer_update`：`{ t: "peer_update", id, seq, ts, mode, x, z, yaw, speed, moving }`——转发的位置包，原样转发，只改 `ts` 为服务器收到时间（供接收方算延迟）。
  - `peer_leave`：`{ t: "peer_leave", id, reason: "quit" | "timeout" | "kick" }`——有人离开，广播。
  - `snapshot`：`{ t: "snapshot", peers: [...] }`——服务器每 5 秒给全员发一次全量快照，兜底丢包（客户端拿它对账：快照里没有的远程玩家删掉，多出来的补上）。
  - `ping / pong`：`{ t: "ping", ts }` / `{ t: "pong", ts }`——心跳（见 3.7）。
3.4.4 服务器永远不转发 `aerial` / `fly` 模式的位置：客户端在 `aerial` / `fly` 模式时**不发 `update`**，只发心跳；服务器收到 `mode` 为 `aerial` / `fly` 的 `update` 直接丢弃（见 §4.7）。
3.4.5 `id` 由服务器分配（`p_` + 6 位随机），客户端不许自报 id；重连恢复时凭 token 认领旧 id（见 3.7）。

### 3.5 发包频率

3.5.1 移动中（`moving` 或速度 > 0.5 m/s）：10 Hz（每 100 ms 一包）。
3.5.2 静止（站着 / 停车）：2 Hz（每 500 ms 一包，只当心跳 + 对账用）。
3.5.3 模式切换（走路↔开车、上车 / 下车）：立即发一包，不等周期。
3.5.4 服务器转发：收到即转发，不做聚合、不做节流（10 Hz × 几十人，单进程足够；见 3.8）。
3.5.5 带宽估算（一条 `update` 约 120 字节 JSON）：20 人同城，每人下行 20 × 10 × 120 B ≈ 24 KB/s，上行 1.2 KB/s；服务器总出向约 480 KB/s——一台 256 MB 小机绰绰有余。

### 3.6 名字与外观

3.6.1 显示名：玩家自己取，默认是 `玩家` + id 后 4 位；上限 12 个字符，只允许中英文 / 数字 / 下划线，其他字符过滤掉；名字只显示在对方头顶的名牌上，不做账号、不做查重（重名就重名，名牌 + 外观种子一起认人）。
3.6.2 外观种子：客户端取服务器分配的 `id` 做哈希，得一个整数 seed；肤色 / 衣服 / 发型 / 身高 / 霓虹胸条全部按这个 seed 从 `people.js` 现有的调色板里取（`SKINS / JACKETS / PANTS / HAIRS / NEON` 五张表，一个字不改），保证同一个人每次进城同一个样子、不同的人样子不同。
3.6.3 车色：本地玩家车固定深蓝 `#16283F`（`playercar.js` 现状）；远程玩家的车用同一车模，颜色按 seed 从 6 个深色里轮换（深蓝 / 墨绿 / 酒红 / 深灰 / 藏青 / 深紫），一眼分得出谁是谁，仍无标无牌。

### 3.7 断线重连与超时

3.7.1 心跳：客户端每 10 秒发 `ping`，服务器 10 秒内回 `pong`；连续 3 次无回（30 秒）客户端判为断线。
3.7.2 重连：指数退避 1 s → 2 s → 4 s → 8 s → 15 s（封顶 15 s），一直重试直到连上或用户切回单机；重连时带上 `resumeToken`（`welcome` 里发的，服务器保存 60 秒），60 秒内重连成功认领旧 id、别人眼里你没离开过；超过 60 秒拿新 id，别人眼里你是“离开又进来”。
3.7.3 服务器清人：15 秒收不到任何包（`update` 或 `ping`）即判超时，广播 `peer_leave(reason: "timeout")` 并删表。
3.7.4 客户端断线表现：断线期间远程玩家冻结在最后位置不动，名牌变灰；重连成功后按新包继续；重连期间本地玩法完全不受影响（单机逻辑本来就独立跑）。
3.7.5 页面关闭 / 刷新：`beforeunload` 里尽力发 `leave`，发不出去由 3.7.3 兜底。

### 3.8 人数上限估计

3.8.1 软上限：单房间 50 人。50 人时每人下行 50 × 10 × 120 B ≈ 60 KB/s，服务器出向约 3 MB/s，Node 单进程仍轻松；瓶颈不在服务器，在手机渲染（见 3.8.3）。
3.8.2 硬上限：单房间 100 人，满了后新 `join` 回 `{ t: "full" }`，客户端提示“城里人满了，稍后再进”并留在单机。
3.8.3 渲染上限（更紧的那个）：每多一个远程玩家，走路是 1 套行人模型（约 10 个 draw call 的实例份额，见 §4.4 做法），开车是 1 辆车（3 个 mesh）；手机上**同时显示的远程玩家封顶 24 个**，按距离取最近 24 个，超出的人只收包、不渲染（名牌和小地图点也不画）；24 个以内手机 draw call 增量可控，超过要实测再定。
3.8.4 远距离降频（上线前做，不在 M1 里）：800 米外的远程玩家，服务器降到 2 Hz 转发；1,500 米外只发快照，不发逐包——留给 M1 之后，设计上先留口子。

### 3.9 以后扩展的口子（只留口子，首版不做）

3.9.1 房间：`join` 里以后加 `room` 字段（默认 `main`），现在全员一个 `main` 房。
3.9.2 兴趣管理：按距离降频 / 不发（见 3.8.4）。
3.9.3 二进制协议：`v: 2` 时 `update` 改 MessagePack / 二进制，`v` 字段就是为这个留的。

## 4. 客户端怎么接（只新增模块，不改现有玩法）

### 4.1 新增文件（3 个，全部是新文件）

4.1.1 `app/multiplayer.js`——多人客户端：建 WebSocket、发 `join / update / leave`、收 `peer_*`、重连、心跳、开关（默认关）。
4.1.2 `app/remote-players.js`——远程玩家渲染：管所有“别人”的模型、插值、名牌（见 4.4、4.5）。
4.1.3 `server/server.js` + `server/package.json` + `server/Dockerfile`——服务端（见 §3.2.4）。

### 4.2 唯一要动现有代码的地方（写代码阶段由总协调排期，周一版之后，改动要最小）

4.2.1 `app.js` 末尾的 `window.__sandbox` 里加两样：`car`（读当前车状态）和 `carGroup`（给 `playercar.js` 的方式 B 用，`playercar.js` 头部注释里本来就写了这个补丁）。现状是两者都没暴露，`multiplayer.js` 拿不到开车姿态，不加这个补丁开车同步做不了。
4.2.2 `people.js` 里把“造一个行人”的几何 / 材质 builder 抽成可复用的导出函数（或 `remote-players.js` 直接 import `people.js` 已有的 `STREET_SEGMENTS / mulberry32` 和调色板，自己拼一套）；**不许动** NPC 那 48 个实例的逻辑、不许动 NPC 的 `tick`。
4.2.3 `playercar.js` 里把内部的 `buildPlayerCar(THREE)` 导出（改一个 `function` 为 `export function`），远程车复用同一车模；本地玩家车逻辑一字不动。
4.2.4 以上三处之外的 `app.js / six-loader.js / index.html` 一个字不许动；多人开关默认关，关了以后沙盘行为和单机版**完全一致**（多人模块不加载、不建连接）。

### 4.3 本地姿态怎么取（每帧读，不改物理）

4.3.1 走路：读 `state.pos`（x、z）和 `state.lookYaw`；发包用的 `yaw` 是行人模型的朝向角——`app.js` 里前进方向是 `(-sin lookYaw, -cos lookYaw)`，而 `people.js` 里模型朝向角 `heading` 满足前进方向 `(sin heading, cos heading)`，所以发包时换算：`yaw = lookYaw + π`（接收方直接当 `rotation.y` 用，不用再换算）。
4.3.2 开车：读 `car.x / car.z / car.heading / car.speed`；`yaw` 直接发 `car.heading`（`carGroup.rotation.y = car.heading`，接收方同样直接当 `rotation.y` 用）。
4.3.3 `y` 不发：接收方用自己的 `groundY(x, z)` 现算地面高（走路 +1.7 眼睛高，开车取地面高）；两边是同一份六区地形，算出来一致，不会有人浮空或陷进地里。
4.3.4 航拍 / 飞行不发包（见 3.4.4、4.7）。

### 4.4 远程玩家长什么样（复用现有建模，不许胶囊人）

4.4.1 走路的远程玩家：复用 `people.js` 的行人拼装（头 + 头发 + 眼睛 + 躯干 + 双臂 + 双腿 + 鞋 + 霓虹胸条），外观按 §3.6.2 的 seed 从现有五张调色板里取；**不许复用 NPC 的 48 个 InstancedMesh 实例**——那是固定池、由 NPC 自己的 `tick` 驱动，远程玩家要自己的一套渲染对象（见 4.4.3）。
4.4.2 开车的远程玩家：复用 `playercar.js` 的 `buildPlayerCar`（见 4.2.3），车里坐一个人——驾驶座上放一个按同一 seed 生成的行人模型（只显示上半身：头 + 躯干 + 双臂扶方向盘的姿态，腿藏在仪表盘下看不见，不用全套步态），车窗是透明玻璃，从外面能看见车里有人。
4.4.3 渲染实现（二选一，写代码时由实现人定，验收标准一样）：
  - 方案 A（推荐）：每个远程玩家一个独立 `THREE.Group`，里面拼 9–10 个小 mesh（复用 `people.js` 的几何形状，材质共享）；24 个远程玩家 ≈ 240 个小 mesh，draw call 偏高，但实现简单、步态好做，M1 先跑通再优化。
  - 方案 B：远程玩家单独开一套 `InstancedMesh`（与 NPC 的 48 个池平行，容量 24），每帧按远程玩家姿态写矩阵；draw call 只有 10 个，但步态矩阵要自己算。M1 之后人多了再切到 B。
4.4.4 切换走路 / 开车：收到 `peer_update` 里 `mode` 变了，远程玩家模型就地切换——走路模型淡出、车模型（含车里人）在同一位置淡入，位置不变（就是对方上车 / 下车的那个点）。

### 4.5 插值与预测（对方动起来要顺，不能瞬移）

4.5.1 接收方给每个远程玩家维护一个位置缓冲：收到包先存起来，不直接贴到模型上；渲染时取“100 ms 前”的两个包做线性插值，位置平滑、朝向用最短弧插值。
4.5.2 预测（dead reckoning）：包与包之间（100 ms 间隔）按最后速度外推：走路沿 `yaw` 方向按 `speed` 前进，开车按 `car.heading` 与 `speed` 前进；超过 300 ms 没收到新包就停止外推、原地待命（不等它瞬移）。
4.5.3 步态：远程走路玩家的摆臂 / 迈腿 / 身体起伏按收到 `speed` 现算，算法与 `people.js` 的 `update` 同款（步频 ∝ speed / 身高 scale）；`moving: false` 时步态停在站立姿态。
4.5.4 车轮：远程车的轮子不转也行（M1 不验收）；车身只跟位置 + 朝向走。

### 4.6 名牌（必须有，不然分不清谁是谁）

4.6.1 每个远程玩家头顶一个名牌：Canvas 画的名字 + 小圆点（在线绿 / 断线灰），做成 `THREE.Sprite`，始终朝向相机；名牌在 300 米外自动隐藏（太远看不清名字，只剩模型）。
4.6.2 名牌不参与碰撞、不挡点击，纯显示。

### 4.7 航拍 / 飞行时的规则

4.7.1 自己在 `aerial` / `fly` 模式时：不发位置包（别人看不见你），但**能看见别人**——远程玩家照常渲染（你在天上看他们走路 / 开车，视角没问题）。
4.7.2 切回 `walk` / `drive` 时：立即发一包 `update`（当前位置），别人眼里你“出现”在那个点；切模式不做平滑过渡。
4.7.3 小地图：远程玩家在小地图上显示为小圆点（颜色按 seed），和本地玩家箭头区分开；M1 只要求圆点出现、位置跟着动。

### 4.8 开关与默认状态

4.8.1 多人默认**关**：进沙盘是单机；设置里加一个“多人在线”开关（或地址栏 `?mp=1`），打开才建连接；关了就断开、清掉所有远程玩家。
4.8.2 连接失败（服务器没起、地址错）：弹 toast“多人服务器连不上，已回单机”，不阻塞进城、不弹错误页。
4.8.3 周一版（2026-11-30）里**没有**多人代码：这三个新文件和 4.2 的补丁都在周一版之后再合入，周一版验收不受多人影响。

## 5. 第一 milestone“同城互相可见”（M1）验收

### 5.1 M1 做完的标准（四条，全过才算过）

5.1.1 两个测试端进同一座城，互相看见对方：A 看见 B 在走路，B 看见 A 在走路，模型是真人行人（有头、衣服、腿在动），不是胶囊人、不是方块。
5.1.2 开车可见：A 开车，B 的屏幕上看见一辆真车在开，车里坐着人；B 开车，A 同样看见。
5.1.3 上下车切换：A 从走路切开车，B 的屏幕上 A 的行人模型变成车（含车里人），位置不变；A 下车，变回行人。
5.1.4 一个端关掉页面，另一个端 15 秒内看见对方消失（名牌和模型一起没）；重新打开能再看见。

### 5.2 测试方法（两个测试端怎么跑）

5.2.1 本地联调（先跑通）：本机起 `server.js`（见 §6.4），电脑 Chrome 开两个窗口（一个正常窗口 + 一个无痕窗口，两个不同的 `id`），都打开 `http://localhost:8000/app/?mp=1`，进城后都切走路，约在星泽广场见面（出生点附近，`x ≈ 0, z ≈ -570` 一带，`people.js` 的 S1 / S4 街段附近）。
5.2.2 局域网真机（再验）：同一 Wi-Fi 下，一台电脑 + 一台手机（林萧的 iPhone 17），手机开 `http://<电脑局域网 IP>:8000/app/?mp=1`，电脑连同一个服务器；手机走路、电脑开车，互相看。
5.2.3 线上（最后验）：服务器部署到 §6 推荐的免费托管后，两台设备都开线上地址，重复 5.2.2。
5.2.4 每一步留证据：每个端截一张对方在视野里的图（共 4 张：A 看 B 走路、A 看 B 开车、B 看 A 走路、B 看 A 开车），加一张小地图双圆点截图；截图里对方头顶名牌要看得清。

### 5.3 M1 验收检查表（验的人逐条打勾）

5.3.1 两端互相看见，真人模型，非胶囊人。
5.3.2 走路步态在动（腿迈、臂摆），不是滑过去的静止模型。
5.3.3 开车对方是真车 + 车里有人，车速和位置与对方操作对得上（对方踩油门，车动起来）。

5.3.5 延迟体感：同一 Wi-Fi 下对方动作延迟 ≤ 300 ms（肉眼看不出明显滞后）。
5.3.6 断线 15 秒内对方消失；重连后能再看见。
5.3.7 单机不受影响：关掉多人开关，沙盘和以前一样，帧率不掉（对照 M1 前的帧率截图）。

### 5.4 M1 不做的事（这次验了也不算数）

5.4.1 不同房间、好友、组队——没有。
5.4.2 语音、聊天、排行榜、账号系统——没有（见 §7）。
5.4.3 碰撞（两辆车撞上、两个人撞上）——没有，模型可以互相穿过，M1 不验收。

## 6. 服务器放哪、怎么部署

### 6.1 硬约束

6.1.1 **不许先买任何东西**：免费开源 / 免费额度 only；要输银行卡才能开的方案先不选（见 6.3 备注）。
6.1.2 **绝对禁区**：短信服务器 RackNerd VPS（`104.223.116.145`，短信监控生产系统）**一个字都不许碰**——不登录、不部署、不装东西、不借它的端口。多人服务器与它没有任何关系。
6.1.3 GitHub Pages（现有线上站）是纯静态托管，放不了 WebSocket 服务器；多人服务器必须另找地方，游戏前端仍在 Pages 上，跨域连 `wss://` 服务器（前端加服务器地址配置，见 6.5）。

### 6.2 三个免费选项对比（额度以 2026-11-26 查到的公开资料为准，部署前在官网再核一次）

| | A. Render Free（推荐） | B. Fly.io Free plan | C. Oracle Cloud Always Free |
|---|---|---|---|
| 免费额度 | 每月 750 实例小时（一个服务跑满一个月刚好够）；0.1 CPU / 512 MB | 每月 $5 用量（2026-11-23 刚恢复的 Free plan；绑卡才有 $5，不绑卡只有 $1 / 7 天试用）；shared-cpu-1x 256 MB 常开约 $2.19/月，$5 够用 | 永久免费：2 台 AMD（1/8 OCPU / 1 GB）+ Ampere 4 OCPU / 24 GB（二选一或组合）；无时间限制 |
| WebSocket | 支持；15 分钟无入站流量（含 WebSocket 消息）后休眠，唤醒约 1 分钟 | 支持；不休眠（$5 额度内可一直开着） | 支持；自己管 VPS，永不休眠 |
| 部署难度 | 最低：连 GitHub 仓库，选 Node 服务，一键部署；不用写 Dockerfile（也可写） | 中：要装 `flyctl`、写 `fly.toml` / Dockerfile，默认起 2 台机器，记得加 `--ha=false` 只留 1 台 | 最高：要开 OCI 账号、配安全组 / 防火墙、自己装 Node、配 systemd + 域名 + 证书 |
| 绑卡 | 不用 | 要绑卡才有每月 $5（不绑卡只有 $1 / 7 天） | 要绑卡验证（只验证，不扣费） |
| 风险点 | 休眠：没人玩 15 分钟就睡，第一个进来的人等约 1 分钟；WebSocket 有消息就不睡，两个人玩着就不会睡 | 额度悬崖：超 $5 自动转按量付费、整月从头计费（官方写明无硬上限）；要盯账单 | 账号开通有审核，IP 难抢（热门区域常没货）；全套运维自己扛 |
| 适合阶段 | M1 测试联机、给林萧演示 | M1 之后长期挂着（绑卡后） | 正式上线、人多了以后 |

### 6.3 推荐

6.3.1 **推荐 A（Render Free）做 M1 和演示**：零成本、不用绑卡、部署最快；休眠问题在演示时不是问题（演示前先打开一个端把服务唤醒；两个人玩着有 WebSocket 消息就不会睡）。
6.3.2 **B（Fly.io）做第二选择**：M1 跑通后、要长期挂着不休眠时切过去；切之前必须先和林萧确认绑卡的事（硬约束 6.1.1 是“不许先买”，绑卡本身不花钱但要他点头）。
6.3.3 **C（Oracle）只做远期备选**：正式上线、人数上来了再考虑；M1 阶段不碰（运维成本最高）。
6.3.4 以上额度都可能变：部署那天在官网 pricing 页再核一次，额度对不上就按 §6.2 的表换一档，换档不用重新设计（服务器就是一个 Node 进程，三个平台都能跑）。

### 6.4 本地开发先怎么跑（不动线上）

6.4.1 起服务器：`cd ~/workspace/virtual-city/server && npm install && node server.js`——监听 `ws://localhost:3001`，终端打印 `listening on 3001` 和每次 `join / leave`。
6.4.2 起前端：`cd ~/workspace/virtual-city && python3 -m http.server 8000`（和现在一样），浏览器开 `http://localhost:8000/app/?mp=1&ws=ws://localhost:3001`。
6.4.3 两个客户端：电脑 Chrome 正常窗口 + 无痕窗口各开一个（两个 `id`，见 5.2.1）；或电脑 + 手机走局域网 IP（手机把 `localhost` 换成电脑局域网 IP，服务器地址同理换 `ws://<电脑 IP>:3001`）。
6.4.4 调试口子：`window.__mp` 暴露连接状态（`connected / id / peers` 数），控制台输入 `window.__mp.peers` 能看到在线表；服务器日志只记 `join / leave / 超速丢包`，不记坐标流水（日志会炸）。

### 6.5 线上部署做法（M1 之后，写代码前不用做）

6.5.1 服务器仓库：`server/` 单独一个 GitHub 仓库（或和沙盘同仓库不同目录，Render 连子目录部署）；Render 上新建 Web Service，环境 Node 20，启动命令 `node server.js`，端口取环境变量 `PORT`。
6.5.2 前端配置：`app/` 里加一个 `mp-config.json`（或地址栏参数）：`{ "wsUrl": "wss://<render 地址>.onrender.com", "enabled": false }`；默认 `enabled: false`，林萧点头才改 `true`，或只在 `?mp=1` 时连。
6.5.3 证书：`wss://` 必须走 TLS；Render / Fly.io 都自带免费证书，不用自己买。
6.5.4 跨域：WebSocket 不受 CORS 限制，但服务器要校验 `Origin`——只放行 Pages 域名（`linx.is-a.dev`）和 `localhost`，其他来源拒绝。

## 7. 边界（多人只做位置 / 动作同步）

7.1 只做：位置同步（走路 / 开车）、朝向、速度、上下车切换、在线 / 离开、名牌。
7.2 不做（以后再说，M1 里一个字都不写）：语音、不做；聊天（文字 / 弹幕）、不做；排行榜、不做；账号系统（注册 / 登录 / 好友）、不做；玩家数据保存（上次位置、服装）、不做；付费、解锁、不做。
7.3 不进周一版：2026-11-30 交的是单机版，多人代码（`multiplayer.js` / `remote-players.js` / `server/` 和 §4.2 的三处补丁）全部在周一版之后再合入；合入时默认关，不影响单机验收。
7.4 不碰的东西：1–4 路的文件、接线（`index.html` / `app.js` 除 §4.2.1 的补丁外）、短信服务器（见 6.1.2）、六区白模数据。
7.5 安全底线：服务器不存任何个人信息（只有临时 id、显示名、外观 seed、最后位置，玩家一走就删）；显示名过滤（见 3.6.1）；不接任何支付和账号；日志不记坐标流水。
